# PWA 安全更新

Web 的更新以当前写作内容可恢复为前提。生产构建使用 `vite-plugin-pwa` 的 `generateSW` 与 `prompt`，由 `src/pwa/` 注册和管理更新；开发服务器不注册 Worker。不使用自动刷新、注销 Worker 或清空站点数据来完成升级。

## 用户流程

1. 新 Worker 安装完成后显示“新版本已准备好”。“稍后”收起提示，保留重新打开入口，不激活更新。首次安装不显示版本更新提示。
2. 用户选择“保存并更新”。图片选择 / 解码 / 写入、文件选择、Markdown / ZIP 导入导出、文章读取 / 保存及目录包维护尚未结束时，明确停止，用户可完成或取消操作后重试。
3. 待更新 Worker 检查同作用域页面，包括尚未受控的页面和不支持新协议的历史页面。只有请求方一个窗口时允许继续；其他标签页或已安装应用窗口必须先保存并关闭。
4. 更新期间应用内容暂时不可交互，显示状态弹窗。浏览器模式复用文章事务队列，目录模式复用现有保存与冲突检查；保存点击时的最新正文、主题及适用的配置，不创建新存储格式。
5. 保存后重新核对文章身份、正文、主题、工作区和操作状态。Worker 激活前再次检查窗口数量，激活并实际控制当前页后再做一次内容核对，最后刷新。
6. 保存失败、权限不足、冲突、工作区变化、Worker 无响应或接管超时均显示错误并恢复交互，不把超时当作成功。提供仅文本导出入口；图片应通过已有 ZIP 或完整目录备份保护。

即使其他原因触发 `controllerchange`，也只提示，不自动刷新该页面。部署导致的动态资源加载错误同样进入用户确认与安全保存流程；应用错误边界的重新加载入口复用该流程。初始化之前的根级崩溃仍由启动错误边界处理。

检查更新发生在注册、恢复联网、重新进入可见状态及每小时；后台检查至少间隔一分钟。网络 / 注册失败可显式重试。仅在已有更新可用或需要重新加载资源时提供“保存并更新”。用户触发的更新准备、保存与接管均有等待上限；保存迟到完成也不会自行启动已失败的更新操作。

## 数据与权限边界

- 不改变数据库名称、schema、存储键、文章 ID、图片路径或目录句柄库；旧 `wemd:preload-reloaded-at` 不再使用，也不清除用户已有配置。
- 更新代码缓存与删除文章数据是不同操作。文章和图片保存在既有 IndexedDB / 目录包中，Blob URL 在重载后按资源重新派生。
- 目录权限由浏览器决定。重载后仍先查询授权；缺权时保留目录模式，用户通过“重新授权原文件夹”恢复，不静默切回浏览器存储、不自动打开选择器。
- 多页面策略为保守阻断，不合并各页未保存内容，也不承诺多标签页协作。窗口列表在检查时成立；其他页面在激活之后才打开时，仍按各页的显式确认 / 保存原则处理，不能把检查称为浏览器全局原子锁。
- 原生关闭标签页、浏览器强退、操作系统终止和磁盘损坏不属于更新流程的保存保证。既有离页提醒和文章恢复机制继续保留。
- 新 Worker 已完成预缓存时可离线切换；尚未下载的新版本无法离线获取。未验证平台仍须单独验收。

## 历史版本首次进入

`81c01e5` 及此前的页面使用独立 `registerSW.js`，没有安全更新提示。新代码不能回填到已经运行的旧页面。

首次迁入需在旧版中完成保存；必要时先导出 ZIP / 完整目录备份，再关闭该站点所有标签页与已安装应用窗口。待新 Worker 自然激活后重新打开，确认正文和图片恢复。仅刷新旧页面可能继续由旧 Worker 响应，不应要求用户清库或在控制台发送激活消息。

此后的版本才使用上述“提示 → 确认 → 保存 → 激活 → 重载”闭环。对历史版本的迁入证据与新流程的后续升级证据分别记录。

## 实现与部署约束

| 位置                                                 | 职责                                                            |
| ---------------------------------------------------- | --------------------------------------------------------------- |
| `apps/web/src/pwa/updateClient.ts`                   | 注册、发现、检查、Worker 通信和实际接管等待；事件本身不能刷新   |
| `apps/web/src/pwa/saveBeforeUpdate.ts`               | 保存前状态检查、复用持久化路径、保存前后及刷新前快照核对        |
| `apps/web/src/pwa/PwaUpdateBoundary.tsx`             | 用户提示、延后、更新期间交互保护、错误与重试                    |
| `apps/web/public/pwa-update-guard.js`                | Worker 内核对同作用域窗口、受控激活，拦截旧 `SKIP_WAITING` 旁路 |
| `articleTransferState`、历史写入队列、目录包操作计数 | 向更新流程暴露内存中的进行中操作，不增加持久化字段              |

`skipWaiting` 和 `clientsClaim` 均为 `false`。Workbox 在默认消息监听器之前导入激活守卫；应用只发送 `RADISHINK_CHECK_UPDATE` / `RADISHINK_ACTIVATE_UPDATE`。不能改回插件的自动接管策略或重新引入自动资源错误刷新。

应用使用部署基路径注册 `sw.js`，设置 `updateViaCache: none`。`sw.js`、`pwa-update-guard.js` 和历史 `registerSW.js` 应允许重新验证，不能套用长期 immutable 缓存。Nginx 模板已单列这些文件；模板检查不等于容器或线上配置已部署。

参考：[Vite PWA 自动更新与表单提示建议](https://vite-pwa-org.netlify.app/guide/auto-update)、[注册方式](https://vite-pwa-org.netlify.app/guide/register-service-worker)、[MDN Clients.matchAll](https://developer.mozilla.org/en-US/docs/Web/API/Clients/matchAll)、[MDN skipWaiting](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting)。具体行为以本仓库锁定的插件版本、构建产物与浏览器证据共同确认。

## 验证与复现

单元 / 组件测试覆盖保存失败、保存期间继续输入与切换文章、忙碌与权限边界、同作用域多页面、消息 / 接管超时、延后、交互恢复、迟到完成，以及资源加载失败不自动刷新。生产验证必须运行固定构建；Vite HMR 不能代替 Worker 升级。

本轮证据见 [2026-10-25 更新记录](../records/2026-10-25-pwa-safe-update.md)。复现步骤：

1. 在历史源码的独立只读来源上构建，将产物复制到临时根目录的 `legacy/`。不要用当前构建冒充历史版本，不重置正在工作的仓库。
2. 在当前源码运行 `mise exec -- node scripts/browser/pwa-upgrade-builds.mjs <临时根目录>`。它构建 `new/`、`next/` 两套 Vite / Workbox 产物，仅在测试入口增加不同标记，形成真实不同的 JS hash 与预缓存清单；不会修改产品源码。
3. 运行 `mise exec -- node scripts/browser/pwa-upgrade-server.mjs <临时根目录> 4183`。服务仅监听 `127.0.0.1`，测试用 POST 接口切换产物，也支持 `/nested/`。不要部署该测试服务。
4. 用独立 Playwright CLI 会话依次执行 `scripts/browser/pwa-upgrade-checks.js`、`scripts/browser/pwa-directory-upgrade-checks.js`。顺序执行，避免共享的版本选择相互干扰。第一组核对历史迁入、后续安全更新、浏览器存储与原图；第二组以原生 OPFS 及明确的选择器 / 权限替身核对目录包、相对部署和触屏布局。
5. 真实系统目录选择、授权和进程重启另外记录；OPFS 权限替身不是系统权限证据。验收结束关闭本次服务与浏览器，证据保留在临时目录或 Git 忽略的 `output/playwright/`。

最后运行 [完整 Web 基线](validation.md)，复查 diff 与未跟踪文件；没有执行的手机真机、Safari / Firefox、真实公众号及线上升级不能写成通过。
