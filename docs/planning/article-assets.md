# 文章目录与图片资源

状态：2026-10-07 规划，尚未实施。用户已明确“一篇文章一个目录、一个 Markdown 文件和 `asset/`”；命名、存储扩展和迁移方案为 P2a 建议。推进顺序见 [工作区计划](writing-workspace-roadmap.md)，ZIP 契约见 [文件进出](markdown-file-import-export.md#下一阶段文章包与文件菜单)。

## 统一文章结构

建议新建 / 导入后的文章采用以下结构，目录名可读但带稳定短 ID，Markdown 文件固定为 `index.md`：

```text
工作区/
└── 春日随笔--a1b2c3/
    ├── index.md
    └── asset/
        ├── image-8d21f4.png
        └── image-b3029a.webp
```

正文示例：

```markdown
![说明](asset/image-8d21f4.png)
```

严格使用用户指定的单数 `asset/`。无图片时也保留空资源目录；ZIP 中保留相应目录条目。

文章 ID、显示标题和目录名分离。改标题不自动改存储身份；显式重命名 / 移动文章时整包处理，Markdown 与资源的相对关系不变。同名通过目录后缀消歧，不覆盖已有包。目录名和资源名过滤分隔符、保留名、控制字符，并处理大小写 / Unicode 冲突；不使用剪贴板原文件名直接拼接路径。

首轮不要求私有 manifest 才能阅读文章，标准编辑器解压后可直接打开 Markdown。服务器所有者、会话、权限等不写进 frontmatter 或导出包；原有未知 frontmatter 继续按既有契约保留。

## 三种存储的物理差异

| 模式       | 文章和图片放在哪里                                                           | 用户可见行为                                                                                            |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 浏览器存储 | 在现有历史文章体系内扩展二进制资源存储，建议 IndexedDB 保存 Blob 与文章归属  | 逻辑上同样是文章包；不会静默写入下载目录或原 `.md` 旁边；导出 ZIP 后才得到磁盘目录                      |
| 本地文件夹 | 用户已授权的工作区内创建真实文章目录，资源写入其 `asset/`                    | 粘贴即复制资源；刷新 / 重开后按权限重新读取，不能依赖临时对象 URL                                       |
| 服务器存储 | Docker 数据卷中按所有者 / 文章 ID 保存 Markdown 与资源，数据库保存索引与版本 | 仅选中服务器模式时上传到自己的后端；访问和导出均校验用户归属，详见 [自托管专题](self-hosted-storage.md) |

普通 `<input type="file">` 选择 `.md` 不授予写入其所在目录或读取相邻图片的能力。目录模式必须取得实际目录授权，且并非所有浏览器都支持；界面按能力解释禁用原因。[MDN 目录选择 API](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker) 说明了安全上下文、用户手势及兼容性限制。

[IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) 可以保存文件 / Blob，但站点数据受浏览器配额、清理和源隔离影响；持久化请求不能替代导出备份。空间不足应明确拒绝写入并保留当前正文，不回退成易失内存后显示“已保存”。[MDN 配额与回收](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## 粘贴与插入图片

1. 捕获当前文章 ID、工作区身份、编辑版本和选区；尚未形成可持久化文章时先创建文章包，失败保持现有内容。
2. 对剪贴板中的实际图片文件校验类型、大小、解码尺寸和数量。建议首轮支持 PNG / JPEG / WebP / GIF；SVG、HTML 伪装图片及其他格式先明确拒绝，避免把活动内容作为图片资源发布。
3. 生成安全且不会覆盖的文件名，把字节复制到当前文章资源存储。相同图片可以在同一文章内去重，不做跨用户共享资源。默认保留原字节、动图和透明度；如需压缩，应有明确选项和结果，不能沿用旧上传链的静默有损处理。
4. 写入成功后，将相对引用加入原编辑位置；使用可随编辑移动的锚点，不能在异步完成时重新使用当前光标。文章切换、选区内容变化、取消或撤销须有明确语义；迟到结果不能插入另一篇文章。
5. 若使用临时占位，原选区必须可恢复，保存 / 导出不能把占位当作真实图片。写入失败恢复对应局部内容，不能覆盖等待期间的新输入；完成写入但已取消插入的资源记为待清理，不立即误删可能已被引用的文件。

剪贴板若只有网页 HTML 或远程图片 URL，没有图片字节，保留相应文本 / 链接并解释未复制资源；不承诺自动下载所有网页图片，也不让后端代抓任意 URL。多张图片按原顺序处理，分别报告失败，不吞掉同次粘贴的纯文本。选图复用相同本地持久化流程；拖入图片可随后接入，不默认扩大为批量文章导入。

建议原型起点为单图 20 MiB、解码 40 百万像素、每次最多 20 张；这些是待测性能限额，不是当前生效规则。浏览器配额、服务器用户配额和文章包上限可能更早阻止写入，最终数值需在 P2a 测量后统一到 UI、存储和 ZIP 校验。

## 预览、复制与路径

- 源 Markdown 始终保存可移植相对路径。预览按当前文章解析资源，派生 Blob URL 或经鉴权的响应；临时 URL 仅存在于视图，切换 / 卸载后释放，刷新重新创建。
- 不能让 `asset/x.png` 落到站点根目录 HTTP 请求，也不能把 Blob URL、本机绝对路径或带会话凭据的 URL 写回正文。
- 读取包内资源时限制在文章根目录，拒绝越界、非法编码路径和符号链接逃逸；旧文相对资源的显式迁移另按下节处理。应用内置装饰图与文章资源保留不同解析来源。
- `resolveImageSourcesForCopy` 目前只把 DOM `src` 转成页面绝对 URL，不具备文章资源读取能力。预览、HTML 复制和公众号复制需明确接入文章资源上下文，继续经过现有 HTML / URL 清理。
- 本地图片预览成功，不证明公众号转存成功。`blob:`、相对路径或带登录的 API 都不能直接当作可公开抓取地址；P2b 必须实测可用的图片复制方式。无法完整复制时，在执行前说明受影响图片并提供导出图片 / 手工插入流程，用户主动选择后才继续；不得显示“完整复制成功”或为此公开私有资源。
- 可评估 HTML 复制时把允许的图片嵌入数据 URL，但须记录体积限制、目标编辑器支持和安全清理结果；不把该建议当作已验证方案。既有公众号行高兼容问题继续独立跟踪。

## 生命周期、旧数据与迁移

目前浏览器文章实际由 `historyStore` / `historyDb` 管理，`StorageAdapter` 只提供字符串读写；不能把新资源写进另一个无人读取的文章库。实施前应定义文章读取 / 保存与资源读写的最小职责，并把两个现有持久化路径接到同一文章契约，不强行将二进制塞进字符串接口。

| 情况                 | 建议行为                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 既有浏览器历史       | 保留原 ID、Markdown、时间、主题与配置键；增量添加资源存储 / 元数据能力，旧纯文本按无资源文章读取                 |
| 历史数量上限         | 区分用户文章与快照；停止自动淘汰用户文章 / 图片。可暂保留 30 篇显式上限，达到时拒绝新建 / 导入并给出处理入口     |
| 旧目录中的散落 `.md` | 保持可读写，不自动移动。首次添加资源时说明并提供“复制为文章目录”，成功校验新副本后才切换，原件保留               |
| 旧文章已有相对图片   | 只从已授权工作区中明确选定的资源复制；无法读取或位于授权边界外时列出缺失项。单文件导入不能凭路径自行读取相邻图片 |
| 既有多 `.md` 目录    | 不把整个目录误认作一篇文章包，更不能删除目录中其他文章；由用户选择主文复制为新包                                 |
| 外链 / 内联图片      | 默认保留已有 URL 或内联源文；下载外链、提取 data URI 是后续显式整理操作，不跟随打开文章自动迁移                  |
| 重命名、移动、复制   | 按文章整体处理；复制生成新文章 ID；操作失败保持原包可用，不把成功创建一半的目标当作完成                          |
| 删除文章             | 说明正文与资源一并删除的范围；只能删除确认属于该文章的包，不能把通用文件夹递归删除当作文章删除                   |
| 删除图片引用 / 撤销  | 不立即删字节，保留撤销可恢复资源；孤立资源的显式清理需先列出候选与引用情况                                       |

浏览器扩展确实需要新增二进制持久化设计，不能沿用上一轮“schema 不变”来虚报零迁移。P2a 先记录版本、备份、旧版读取边界、升级中止与重试、多标签页占用时的处理；失败不清库重建。升级前提示导出备份，旧版本不能理解新数据时停止写入并提示使用兼容版本，不假设数据库可以自动降级。

资源先落盘再引用，未完成操作有可识别的暂存状态；浏览器同库尽可能使用事务，本地文件系统用写入日志 / 临时文件与可恢复步骤实现一致性，不声称跨文件原子提交。磁盘满、权限撤回、页面关闭、双标签编辑与外部编辑器修改均需处理；保存前检查版本 / 原内容，冲突保留两份而非静默覆盖。

## 验收重点

两种现有存储均完成：粘贴 → 保存 → 刷新 / 重开 → 预览 → 改名 / 移动 → ZIP 导出 → 在另一种存储导入。逐字比较正文与未知元数据，逐字节比较资源；删除、撤销、重名、相同图片和缺失资源分别验证。

负向用例包括配额 / 磁盘满、权限撤回、上传中切换文章 / 工作区、处理中继续输入、写入部分失败、恶意路径、伪装图片、大尺寸图片和迁移中断。目录 API 替身不能代替系统真实授权；Chromium、无目录 API 的浏览器与手机下载分别记录，公众号图片转存另留实际证据。
