# 插件系统规划

状态：未来规划，尚未提供用户插件安装、公共 SDK 或第三方代码加载能力。本文列出方向、职责和进入实施前的条件，不冻结具体 API。

## 目标与现有基础

让排版与写作能力能以明确的扩展点演进，减少为单项功能改动编辑器、解析器和复制服务的需要。插件首先服务真实的扩展需求，保持正文可编辑、默认排版可用，以及预览与公众号复制结果可解释。

`packages/core/src/MarkdownParser.ts` 目前通过 `markdown-it` 注册内置语法扩展；图床适配器、主题和 AI 设置也已有各自职责。这些内部实现不等于面向用户的插件平台，不应只给现有模块加一个“插件”名称就宣称系统完成。

基础编辑、本地草稿、默认渲染、公众号复制及 [Markdown 文件导入导出](markdown-file-import-export.md) 仍由产品直接保证。现有主题和服务配置不能因插件化被擅自删除或要求重新录入。2026-10-07 用户另行要求停用图床 / AI 产品功能，按 [界面专题](editor-interface.md) 执行，保留旧配置不代表继续启用服务；插件规划不恢复已移除功能，也不作为文章资源或服务器存储的前置依赖。

## 扩展范围与推进顺序

| 阶段             | 候选范围                                                            | 进入条件                                             |
| ---------------- | ------------------------------------------------------------------- | ---------------------------------------------------- |
| 内部扩展点       | 从一个真实的内置语法 / 排版扩展出发，梳理输入、输出、顺序和失败处理 | 核心预览 / 复制链路稳定，有可复现的回归样例          |
| 随产品分发的扩展 | 明确声明、配置、启停、兼容检查和升级；随源码审阅及构建分发          | 同一扩展在预览与复制中的行为一致，禁用后文章仍可编辑 |
| 第三方扩展       | 按明确授权范围运行，具备来源、完整性、隔离和恢复机制                | 隔离原型与威胁分析通过，权限能由宿主实际执行和限制   |
| 分发与生态       | 按需求评估安装、升级、开发文档和分发渠道                            | 生命周期和 API 版本已被实际扩展验证，不先建设市场    |

优先候选是受约束的 Markdown / 排版扩展与用户主动触发的文章处理命令。主题包、文件格式转换、图片服务或 AI 扩展是否纳入统一模型，需由实际重复职责证明；不预设所有能力共用一个大而全的插件接口。

首轮不引入插件市场、远程 URL 任意脚本加载、自动更新、账号体系或云端执行服务。后续需要这些能力时另行设计其产品和运行边界。

## 职责划分

- `packages/core` 负责可复用的解析 / 转换契约及确定的执行顺序，不直接控制浏览器界面、工作区或用户设置。
- `apps/web` 负责启停与配置界面、用户交互、受约束的宿主能力、错误反馈和任务取消。
- 预览、HTML 复制与公众号复制消费同一份明确的扩展配置；不各自隐式加载不同插件。
- 插件通过已声明的宿主接口申请必要能力，不直接依赖编辑器 store、内部 DOM 结构或存储键。接口范围由首个实际扩展原型确定，避免空转包装层。
- 扩展输出进入最终 DOM 或剪贴板前，仍经过现有 HTML / URL 清理及复制兼容处理；插件不能关闭这些边界。

## 执行与一致性

执行链需明确各扩展处于原文变换、解析、排版还是最终复制准备阶段，并规定顺序与冲突处理。改变源 Markdown 的命令应支持预览差异和撤销；纯显示扩展不能静默改写文章。

一次预览 / 复制任务使用固定的文章、主题及插件配置快照。配置变化、插件关闭、异步结果迟到或工作区切换不能把过期结果写入当前任务；取消、超时及异常都必须有可见语义。

插件失败时保留正文，并允许禁用有问题的扩展后恢复编辑。复制或导出缺少必要扩展时不得静默省略内容后报告成功；需要说明受影响部分，并由用户选择修复、禁用或接受明确的降级结果。

## 权限与隔离

第三方脚本与宿主在同一 JavaScript 环境执行时，不能仅靠 TypeScript 类型、manifest 或 HTML 清理宣称隔离。输出清理也不能阻止脚本读取宿主数据；隔离执行方式与通信契约必须在允许加载第三方代码前验证。

需要分别设计文章读取、文章修改、文件访问、网络、剪贴板、配置和插件存储的能力边界。默认不授予未声明能力；权限提示必须说明数据和用途，撤销后立即阻止后续调用。凭据不直接交给插件，必要的外部请求经具有明确边界的宿主能力完成。

插件状态与用户文章分开保存。禁用或卸载不删除正文；清除插件数据须说明影响。任何新增存储 schema 都要记录迁移、回退与版本兼容，不更改现有草稿键来强迫迁移。

## 兼容、来源与分发

插件声明预计需要稳定标识、版本、宿主兼容范围、扩展点、配置 schema 和所需能力，但字段名称及插件版本规则待原型后冻结。重复标识、缺失依赖、不兼容版本与能力冲突必须显式拒绝，不能自动选一个版本掩盖问题。

公共 API 的兼容窗口、弃用提示和配置迁移方式应先形成约定，再发布 SDK。产品 Git / Docker 版本继续遵循现有 [版本规则](../governance/versioning.md)，不把内部插件协议版本混同为产品发布标签。

随产品分发的插件沿用代码审阅、依赖锁定、许可声明及构建检查。未来独立安装的插件需要记录作者、来源、许可、包摘要和更新变更；网络下载、升级及权限扩大必须是用户可知的行为。

## 验证与实施前决策

| 验证方向   | 必须覆盖的结果                                                            |
| ---------- | ------------------------------------------------------------------------- |
| 生命周期   | 启用、配置、关闭、升级失败与恢复可重复，插件关闭后基本编辑仍可用          |
| 排版一致性 | 标题、列表、代码、表格、公式、Mermaid、图片在预览和两种复制中有可追溯结果 |
| 冲突与兼容 | 重复注册、顺序冲突、缺失依赖、不兼容宿主和旧配置不能静默成功              |
| 失败处理   | 抛错、超时、取消、过期结果不破坏正文，不把缺失内容的复制当作成功          |
| 安全边界   | 活动 HTML 输出被清理；第三方隔离另测越权、通信伪造及撤销后的访问          |
| 性能与资源 | 插件数量、长文章和高频编辑下的时间 / 内存预算有测量，禁用后释放监听与任务 |
| 来源       | 分发包与审阅来源、依赖和许可声明一致，不能从未确认 URL 隐式加载代码       |

进入实现前先选定一个实际扩展，完成生命周期和预览 / 复制共用契约原型，再决定是否值得抽出公共扩展接口。第三方隔离技术、可调用能力、性能预算、API 兼容周期和分发形式仍为待决事项。实施验证遵循 [验证基线](../development/validation.md)，不得以内部单测替代真实编辑器和公众号效果验收。
