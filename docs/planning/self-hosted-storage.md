# 自托管部署、服务器存储与账号

状态：2026-10-07 规划，尚未实施。用户已明确两种部署形态、可选账号隔离，并补充 Radish OIDC 登录；本文的后端、数据布局、配置字段和接口均为建议，进入 P3 前以原型和 ADR 收敛。阶段顺序见 [工作区计划](writing-workspace-roadmap.md)。

## 部署能力矩阵

| 能力                 | Vercel 纯静态前端            | Docker Compose 前端 + 后端                                         |
| -------------------- | ---------------------------- | ------------------------------------------------------------------ |
| 浏览器存储           | 提供                         | 提供，仍留在当前设备                                               |
| 本地文件夹           | 浏览器支持且用户授权时提供   | 同样受浏览器能力与目录权限限制                                     |
| 云端（自托管服务器） | 不提供，也不默认探测外部 API | 后端能力有效时提供；数据在部署者自己的服务器                       |
| 账号密码             | 不提供                       | 可启用，按用户隔离服务器文章和资源                                 |
| Radish OIDC 登录     | 不提供                       | 账号系统启用并完成 Radish 客户端配置后提供，与本地登录共用用户归属 |
| 图片资源             | 浏览器 / 本地目录内保存      | 按所选模式保存，选择服务器模式才上传                               |
| 多端离线同步、协作   | 不提供                       | 首轮也不提供；联网访问同一服务器工作区不等于同步本地工作区         |

界面可命名“云端（自托管服务器）”，说明不是 RadishInk 官方托管服务。切换模式不自动搬迁文章；跨模式迁移首轮通过单文章 ZIP 或明确的复制操作完成，禁止静默上传整个本地工作区。

## 现有代码不能直接当作后端产品

根 `docker-compose.yml` 当前只有 `web` 服务，属于静态前端镜像模板；Docker 发布工作流仍停用。`apps/server` 是保留的 NestJS 上游图片服务，现有 `/api/upload` 与公开 `/uploads/` 没有文章归属或账号隔离，部分 service 方法是占位返回，不能复用后就宣称服务器存储已完成。

建议优先评估沿用 NestJS / TypeScript，增加真实文章与资源模块，收束或停用旧公共上传路径；不因参考兄弟项目引入另一套语言或多服务架构。首轮按单实例设计：前端负责静态页面和同源反代，后端负责账号、文章 IO、鉴权、版本与资源。SQLite 可作为账号、会话和索引的候选，Markdown / 图片在数据卷；SQLite 驱动、迁移工具、依赖许可及锁文件变化在实施时确认。

## 同源入口与能力发现

建议同一个公开域名分路：`/` 到前端，`/api/` 到后端；HTTPS 在部署者的反代终止，内部容器网络使用 HTTP，后端端口不直接暴露公网。前端镜像通过运行时公开配置识别 `static` / `server` 形态，避免为每个域名重建镜像；所有密钥只存在后端配置和持久化存储。

```text
浏览器 ── HTTPS ── 部署入口 / web
                         ├── /       静态前端
                         └── /api/   server ── 数据卷（索引、文章、asset）
```

- Vercel 固定为静态形态，不显示服务器选项，不因用户文章失败而自动切到服务器，也不允许单填任意地址就变成第三种部署形态。
- Compose 形态先请求版本化的能力端点（建议 `/api/capabilities`），返回服务器存储可用性、账号模式、协议版本和上传限制；这不是认证凭据，也不代替每个 API 的授权检查。
- 无后端、超时、返回 SPA HTML、版本不兼容或维护中时，服务器选项显示具体不可用原因和重试入口。已经选中服务器时，断线保留正文并显示未保存，允许导出抢救；不伪装保存成功、不静默转到浏览器库。
- 切换模式先处理旧稿保存和未完成资源写入，确认新目标可用后提交切换，沿用现有工作区身份保护。重登录与切换账号也属于身份变化，晚到响应不可写入另一个用户界面。
- 同一浏览器的本地草稿不自动成为登录用户的私有数据。账号切换清除旧用户服务器响应、Blob URL 和缓存，不把未保存私有正文留给下一用户；切换前明确保存 / 导出 / 放弃。通用本地工作区仍按设备 / 站点隔离，界面需说明。
- PWA / Service Worker 不缓存认证 API、私有文章、资源响应和会话；登出后验证后退、离线与旧标签页不会重新显示其他用户私有内容。

## 账号启用与关闭

账号系统支持两种登录方式：本地账号密码和“使用 Radish 登录”（OIDC）。建议 Compose 默认启用本地账号密码，Radish 登录由部署者配置后启用；两者可以并存，也可在确认恢复路径后仅启用 Radish 登录。账号系统开启时至少保留一种有效登录方式，配置错误不得降级为无账号共享模式。

首个管理员通过受控本机初始化命令或一次性引导流程创建 / 指定，不提供固定默认密码，也不把首位 OIDC 登录者自动设为管理员。首轮关闭公开注册，由管理员创建 / 禁用用户与重置本地密码；忘记密码提供部署者可执行的恢复命令。不先接邮件服务、Radish 之外的身份提供方、组织、计费或复杂权限系统。Radish 登录的准入与账号关联见下节。

账号启用后，所有服务器文章、图片、列表、搜索、改名、删除和导出都按登录会话确定 `ownerId`；不能信任客户端提供的用户 ID 或仅在列表中隐藏。访问不属于本人的资源返回不泄露内容的错误；管理员管理账号不自动取得阅读全部文章的产品入口。

密码使用成熟库实现带独立盐的慢哈希，建议 Argon2id，参数在实现时依据运行资源测量；不保存明文、可逆密文或前端发来的固定哈希作为口令替代。[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

浏览器会话建议使用 `HttpOnly`、生产 `Secure`、合适 `SameSite` 的 Cookie，服务端保存可撤销会话；登录时更换会话标识、登出 / 禁用 / 重置密码时撤销，并设空闲及绝对时限。写入接口检查来源和 CSRF，登录限速，配置可信反代，避免把 Token 放进图片 URL、导出包或日志。[OWASP 会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

**明确关闭账号后是共享工作区，不存在用户隔离。** 建议仅供本机 / 可信私网，使用固定内部所有者标识；默认 Compose 仅绑定 loopback，由部署者主动配置网络入口。任何能够访问它的人都具有该共享区权限，不能用浏览器随机 ID 冒充鉴权。

账号开关仅由部署配置控制，前端不能自行关闭。开启前已有共享文章时，先备份并显式指定归属账户；多用户切换为无账号时默认拒绝，要求先完成导出 / 归属迁移，不自动合并为公开文章。配置改变不允许绕过现有数据的隔离约束。

## Radish OIDC 登录

### 接入职责与现有依据

Radish 作为身份提供方，RadishInk 作为独立 OIDC 客户端；Radish 负责验证其账号，RadishInk 仍负责本地用户、会话、文章归属和配额。只获取登录所需身份，不同步 Radish 的文章、附件或管理员权限，也不读取它的用户数据库和密码。

2026-10-07 只读核对了兄弟项目 `Radish.Auth/Program.cs`、`OpenIddict/OpenIddictSeedHostedService.cs`、`Controllers/AccountController.cs`、`Controllers/AuthorizationController.cs`、`Radish.Api/Controllers/ClientController.cs` 及 `Docs/guide/authentication-service.md`：已配置授权码、Token、UserInfo、EndSession 端点，既有公开客户端要求 PKCE，正常登录将用户 ID 写入 `sub`，客户端管理支持 confidential client 与密钥轮换。这只是本地代码依据，尚未针对真实发行方验证发现文档、独立客户端注册和完整登录往返；不能据此宣称已经联通。

RadishInk 后端建议作为 confidential client 使用 Authorization Code + PKCE S256，负责发起授权、回调换码和会话建立；浏览器仅持有 RadishInk 的会话 Cookie，不保存客户端密钥或 Radish Token。采用成熟 OIDC 客户端库，不自行拼接 JWT 验证逻辑；协议取舍依据 [OAuth 安全最佳实践](https://datatracker.ietf.org/doc/html/rfc9700#section-2.1.1)。

### 配置与登录流程

| 配置           | 规划要求                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 登录开关       | 本地密码和 Radish OIDC 独立启停，受账号总开关约束；能力端点只返回可展示的登录方式                                                          |
| Issuer         | 部署者配置可信 Radish 公开发行方地址，严格匹配发现文档与 ID Token 的 `iss`；不接受终端用户提交任意发现 URL                                 |
| Client         | 在 Radish 注册独立应用（建议 client ID `radishink`，实际值以注册为准）；不复用 `radish-client` / Console 的身份、密钥或回调                |
| 客户端凭据     | 按注册的客户端认证方式配置在 RadishInk 后端；生产 secret 通过受控秘密配置提供，支持轮换，不进前端、Git、日志或镜像                         |
| 回调与退出返回 | 注册精确的 RadishInk 后端回调 URI 与退出返回 URI，建议 `/api/auth/oidc/radish/callback`；生产用 HTTPS，无通配符；开发和生产客户端分开      |
| 权限           | 默认只申请 `openid profile`；有明确用途再申请 `email`，不为登录请求 `radish-api`；首轮不默认申请 `offline_access` 或长期保存 Refresh Token |
| 首次准入       | 建议邀请 / 管理员批准后才启用服务器文章权限；允许所有 Radish 用户首次登录自动开通必须是部署者的显式选择                                    |

协议端点与签名公钥从受信任发行方的发现文档获取，不把本地源码里的路径拼成对所有部署都成立的地址；后端校验 HTTPS、发行方一致性、响应格式及超时，处理公钥轮换。[OIDC Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata)

登录按钮先保护当前未保存稿件，再跳转 Radish。后端生成并保存短时、一次性的 `state`、`nonce` 和 PKCE verifier，绑定发起浏览器及固定回调；回调成功、失败或取消均消费该次尝试，拒绝重放。返回编辑器的地址只允许受约束的站内相对路径，授权取消 / 超时不丢失原稿。

回调验签并校验 `iss`、`aud` / `azp`、有效期、`nonce` 及授权码归属；读取 UserInfo 时还需确保其 `sub` 与 ID Token 相同。校验完成并通过本站账号状态 / 准入检查后，才轮换并创建 RadishInk 会话。验证要求以 [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation) 为依据。

### 用户归属与绑定

每个 RadishInk 用户拥有独立内部 ID，文章只关联该 ID。外部身份以精确的 `(issuer, subject)` 对映射到内部 ID，并有数据库唯一约束；邮箱、昵称及显示名可变，不能用于自动合并，即使邮箱已验证也不例外。[OIDC 稳定身份标识](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)

- 同一个 Radish 身份重复登录回到同一个本站账户；名字或邮箱变化只影响展示，不新建文章归属。
- 绑定既有本地账户时，先登录并重新验证本地账户，再完成一次新的 Radish 授权确认；不能只输入邮箱就取得已有文章。该外部身份若已绑定其他账户，拒绝并提示人工处理，不合并两份数据。
- 解除绑定需再次验证当前身份，并保证还有可用登录 / 管理员恢复路径；只有 OIDC 身份的账户不自动生成密码。设置本地密码必须走明确的验证流程。
- Radish 的角色声明不自动映射为 RadishInk 管理员；本站禁用账号即时撤销本站会话，不能再次通过 OIDC 绕过。
- 发行方域名 / subject 规则变化需要受控映射迁移和备份，不按相同邮箱重新认领旧文章；删除再注册的 Radish 账户也不能因邮箱相同继承数据。

### 退出与可用性

默认“退出 RadishInk”仅撤销本站会话并清理私有缓存。若提供“同时退出 Radish”，必须是明确选项，按发现的 EndSession 能力和已注册返回地址执行；退出 Radish 可能影响其他应用的单点登录体验。[OIDC RP-Initiated Logout](https://openid.net/specs/openid-connect-rpinitiated-1_0.html)

Radish 不可用时明确显示登录失败 / 重试；已启用的本地密码入口仍可用，不临时开放共享区。仅 OIDC 部署应提供部署者通过本机管理命令恢复管理权的路径，不留隐藏网络免密入口。本站已有会话遵循有界有效期，不因上游短时不可用直接丢弃当前编辑。

不能承诺“退出 / 禁用 Radish 账号立即退出所有 RadishInk 会话”：这需要另行验证上游撤销通知或定期重新认证策略。首轮在 P3 冻结本站会话上限与重新认证周期并记录传播延迟；Back-Channel Logout 等能力未经发现和实测不声称支持。

### 实施与验收

纳入 P3，可先完成内部用户 / 本地登录，再接 Radish OIDC，P4 交付两种登录方式的配置说明。真实联调需要 Radish 侧注册独立客户端、实际 Issuer 和回调；这些值本轮不猜测、不收集密码、不创建应用，也不修改兄弟项目或部署配置。

验证本地登录 / OIDC 并存、仅 OIDC、两种登录关联同一内部用户、两个 Radish 用户文章隔离、同邮箱不合并、绑定冲突、首次准入、本站禁用和取消登录。增加错误签名 / Issuer / audience / nonce、state 与授权码重放、回调开放重定向、公钥轮换、密钥轮换及上游超时的负向用例；检查浏览器持久存储、业务 URL、日志和前端产物不含 Token 或客户端秘密。退出协议如需 ID Token hint，单独核对传输方式和脱敏，不把它拼进普通业务链接。开发替身通过后仍需真实 Radish 往返登录 / 退出证据。

## 服务器文章与一致性

数据布局建议如下，路径只由服务端验证过的 ID 构造：

```text
/data/
├── metadata.sqlite
└── users/
    └── <owner-id>/
        └── articles/
            └── <article-id>/
                ├── index.md
                └── asset/
```

Markdown / 资源字节以文件为真值，数据库存所有者、索引、版本和状态；如何重建索引和恢复未完成写入要有明确实现。MD 与数据库不具备天然跨介质事务：使用暂存、原子文件替换、操作状态和启动恢复步骤，失败不得更新为“已保存”。正式备份需一致地涵盖索引和文件。

首轮接口职责包括：能力 / 健康检查、登录 / 登出 / 当前会话、文章列表及 CRUD、资源写入与授权读取、整包导入导出。具体路由和 schema 在 P3 冻结，不能只加一个 `server` 存储枚举或空壳适配器。

- 写入带文章版本 / `If-Match` 等等价前置条件；两个标签或设备同时编辑时返回冲突并保留本地副本，不使用最后请求无条件覆盖。重试创建 / 资源写入要有幂等身份，避免超时重试产生重复文章。
- 所有 IO 校验文章归属和路径边界；图片不通过匿名静态目录公开，读取时鉴权，设置私有缓存策略。随机文件名不是访问控制。
- 上传限制同时覆盖单资源、文章总量、用户总量、解码尺寸及请求并发；反代限制与后端一致，失败返回可识别原因。首轮只接收客户端提供的字节，不代抓任意远程图片 URL。
- 删除文章与资源有明确范围、确认和恢复 / 备份边界，不能删除其他所有者或遗留共享文件。临时文件回收不抢删未完成或仍被引用的资源。
- 服务器不会读取浏览器本地目录；服务器磁盘也不挂载进前端静态目录。公众号转存限制沿用 [资源专题](article-assets.md#预览复制与路径)。

## Compose 与运维交付

首轮尽量保持 `web` + `server` 两个应用服务，数据库若采用 SQLite 则无需独立数据库容器。是否需要一次性迁移服务由数据库方案决定；不提前引入 Redis、对象存储、独立 Auth 或 Gateway。

需要随 P4 一起交付：

1. 前后端构建入口、Compose 与不含真实秘密的配置示例；固定镜像版本按 [版本规则](../governance/versioning.md) 对齐，区分本地构建验证与拉取发布镜像。
2. 数据卷位置、容器用户 / 文件权限、健康检查与启动顺序；后端准备好且迁移成功后才接收写请求。Compose 的启动不等于服务 ready，需明确健康条件。[Docker 启动顺序说明](https://docs.docker.com/compose/how-tos/startup-order/)
3. 首次管理员初始化、禁用账号、口令恢复、Radish OIDC 独立客户端与回调配置、域名 / HTTPS 和密钥持久化 / 轮换说明；不在镜像层或前端环境变量里放凭据。
4. 升级前备份、迁移锁、失败退出、兼容版本与回退条件；不可逆数据迁移不能仅靠换旧镜像回滚。拒绝旧服务写入不兼容 schema。
5. 一致备份与恢复：暂停写入或提供一致快照，同时保存数据库、文章、资源和必要配置；恢复到空实例检查登录、所有者、正文与图片字节。容器重建成功不等于备份有效。
6. 结构化错误日志、健康状态、磁盘 / 配额提示及清理策略；日志不包含正文、图片字节、密码或会话凭据。

当前 Docker 发布仍停用。进入 P4 时同步代码、部署说明、验证命令和仓库发布检查，按授权恢复对应后端 / 镜像流程；不能只修改 Compose 或放宽现有暂停门禁。

| 方向         | 必须证明                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 两种形态     | Vercel 无后端仍完整编辑 / 保存 / ZIP 进出；Compose 后端缺失或不兼容时禁用云端，不影响现有两种存储        |
| 用户隔离     | A 无法枚举、读取、覆盖、删除、下载或打包 B 的文章和图片，包括猜测 ID、路径越界和直接资源 URL             |
| 会话         | 失效、登出、禁用、密码重置、CSRF、限速和账号切换正确；旧响应与 PWA 缓存不串用户                          |
| Radish OIDC  | 真实登录 / 退出、绑定与准入、发行方 / Token / 回调负向测试、上游故障及无密钥泄露；本站隔离不依赖上游角色 |
| 保存         | 网络断开、请求超时重试、磁盘满、数据库忙、上传部分失败与版本冲突均保留当前内容并报告未保存               |
| 数据生命周期 | 开关账号不能意外公开旧数据；删除、迁移、升级失败和索引恢复可解释、可重试                                 |
| 部署         | 全新安装、重启 / 重建、卷持久化、健康检查、备份恢复到新实例实际通过                                      |

服务端 build / 单元 / API 集成 / 多用户负向测试及真实 Compose smoke 需纳入新的验证命令；现有 `validate:web` 不包含后端，不能作为服务端验收证据。跨设备验证和公众号粘贴仍分别记录，不以登录成功替代文章隔离或数据恢复测试。
