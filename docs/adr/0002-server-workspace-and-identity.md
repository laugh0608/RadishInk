# ADR 0002：服务器工作区、提交边界与账号归属

日期：2026-10-25。状态：采用为 P3 实施方向；P3-1 持久化、P3-2 本地账号 / HTTP 与 P3-3 Web 已实现并经本地验证，见 [P3-3 记录](../records/2026-10-25-server-web-workspace.md)。OIDC 与 Compose 尚待实施。

## 背景

P2 已提供浏览器 / 本地目录文章包，`ArticleStore` 的提交单元包含正文、全部保留资源和已读版本。P3 要增加主动选择的服务器工作区、本地账号与 Radish OIDC；P4 再交付 Compose。既有 NestJS 服务仍是无归属的图片上传实现，不能直接开放为服务器工作区。

产品范围以 [自托管专题](../planning/self-hosted-storage.md) 为准；实施契约集中在 [P3 服务器契约](../planning/server-workspace-contract.md)，实验结果见 [决策验证记录](../records/2026-10-25-p3-design-probe.md)。本文记录选择及原因，已实现范围与对外开放范围以当前状态为准。

## 决定

### 技术与进程

沿用 `apps/server` 的 NestJS 11 / TypeScript 和项目 Node 22，单实例、单写入服务、同机本地持久卷；前端与 API 同源。使用 SQLite 保存账号、会话、授权归属、已提交版本指针和可重建的列表索引；Markdown 与资源字节保存为文件。不引入 Redis、独立数据库服务、对象存储或另一套后端语言。

正式驱动选择 `better-sqlite3`，迁移使用有版本、摘要和事务的显式 SQL，不先引入 ORM。同步数据库操作限制为短事务，摘要计算、图片检查和文件 IO 放在事务外；忙碌返回可重试错误。运行时使用 WAL、外键、`synchronous=FULL` 和有界 busy timeout，拒绝多实例及网络文件系统配置。SQLite WAL 的同机约束与备份时 WAL 的处理要求见 [官方说明](https://www.sqlite.org/wal.html)。

早期决策实验使用项目已有 Node 22.23.3 的 `node:sqlite`。它在 [Node 22 文档](https://nodejs.org/download/release/latest-v22.x/docs/api/sqlite.html) 中仍标为实验能力，**不据此把它选为生产驱动**。P3-1 后续接入固定版本的 `better-sqlite3` 并验证 Linux x64 / arm64 原生运行，具体版本、安装期兼容处理和证据统一见 P3-1 记录，不能从 macOS 原型推导容器兼容。[驱动说明](https://github.com/WiseLibs/better-sqlite3)

口令选择 `argon2` 的 Argon2id，OIDC 选择 `openid-client` v6 系列；P3-2 已固定安装 `argon2@0.45.1` 并记录双架构实测，`openid-client` 尚待 P3-4 安装；精确版本、传递依赖许可和运行检查随各切片同步清单与锁文件。服务端现有 `nodenext` 编译配置可保留，OIDC 模块以动态 `import()` 接入并验证编译产物，避免依赖 CommonJS 自动加载 ESM 的隐含版本条件。[argon2](https://github.com/ranisalt/node-argon2)、[openid-client](https://github.com/panva/openid-client)

### 提交与文件真值

采用不可变资源对象、不可变正文快照、SQLite 当前版本指针：

1. 验证请求、会话、文章归属、已读版本和配额；将新资源与正文写入同卷暂存区，计算并校验摘要。
2. 资源按文章内摘要存储；既有对象先核对字节，不能同名覆盖。新快照包含完整资源路径清单及正文 / 元数据摘要。写入并同步文件、目录，再发布不可变快照。
3. 在短事务中重新检查会话有效性、归属、版本、幂等记录和配额，将版本指针、索引、计量与提交回执一起提交。成功响应只发生在事务提交之后。
4. 崩溃后只读数据库指向且完整性校验通过的快照；未引用对象或快照保留为待检查孤儿，不选择“目录里最新一份”恢复。响应丢失时依靠幂等回执确认结果。

数据库事务不包裹文件系统事务；这是一种文件先持久化、数据库最后发布可见状态的协议，不能称为跨介质原子事务。断电持久性仍依赖操作系统、文件系统与存储设备正确实现同步语义；实验中的 SIGKILL 不等于断电验证。[SQLite 原子提交边界](https://www.sqlite.org/atomiccommit.html)

“文件保存正文真值”不等于数据库可以丢弃。用户、会话、身份映射、当前提交指针及删除状态是数据库中的权威状态；仅列表派生索引可从已确认快照重建。数据库丢失必须恢复一致备份，不能扫描孤儿文件推断文章归属或提交成功。

### 身份与隔离

每个文章只有一个内部所有者。所有服务方法接收由有效会话确定的内部身份，SQL 查询和文件定位同时约束所有者；HTTP 输入不得指定 `ownerId`。管理员只获得账号管理能力，不自动拥有文章读取接口。

本地账号和 Radish OIDC 共用内部用户；外部身份唯一键为精确 `(issuer, subject)`，不按邮箱关联。采用后端授权码交换、PKCE S256、一次性 state / nonce 和可撤销 Cookie 会话；不将访问 Token 用于文章 API。首次管理员由本机命令创建，公开注册关闭，OIDC 新身份默认等待管理员准入。会话与准入参数见实施契约。

无账号模式是显式的共享工作区。账号模式写入部署元数据，运行配置变化不能自动改变旧数据的可见性；有数据时必须经过停写、备份和归属迁移。OIDC 故障、配置缺失、数据库失败都不能降级为共享访问。

### 前端边界

服务器模式复用 `ArticleStore` 与文章资产预览 / ZIP 能力，通过真实 `ServerStorageAdapter` 接入，不只增加枚举。实例绑定部署身份、用户、工作区及文章；账号变化和恢复备份后必须失效旧实例。服务器错误保留未保存正文，不回落到浏览器库。

静态部署保持无账号、无 API 探测；仅明确启用服务器形态后读取能力。所有认证 API、文章、图片都排除 Service Worker 与 HTTP 缓存；ZIP 继续由前端从同一已验证快照生成。登录不上传现有浏览器文章，跨模式首轮使用已有 ZIP 导入为新文章。

## 未选择的方案

| 方案                                     | 取舍                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------- |
| 直接扩展公开 `/api/upload` / `/uploads/` | 无文章归属与一致性；正式 P3 启用前撤下这些路由，旧上传不自动认领      |
| Markdown 与图片全部放进 SQLite BLOB      | 可简化事务，但不符合既定文件卷方向；先保留文件可检查性与标准 ZIP 迁移 |
| 原位覆盖 `index.md` 后更新数据库         | 崩溃时可能出现新正文与旧版本，需复杂回滚；采用不可变快照及指针发布    |
| 每次保存复制全部图片                     | 自动保存会重复占用磁盘；文章内不可变对象复用字节，快照只引用摘要      |
| 全局内容去重或公共图片 URL               | 增加跨用户存在性、授权与垃圾回收复杂度；资源仅在同一文章内复用        |
| 无期限 JWT / 浏览器 localStorage Token   | 禁用、密码重置和退出不易即时撤销；使用服务端会话                      |
| PostgreSQL / 多副本                      | 首轮规模和交付不需要；突破单机写入范围时另做 ADR 与迁移               |

## 后果与实施门槛

保存协议增加快照、幂等回执与垃圾回收责任，但冲突、重试和崩溃可明确解释。旧快照不是面向用户的版本历史产品；正式实现须有物理容量限制和停写清理工具，不能无限保留而声称只计当前文章大小。

P3 分为基础持久化、本地账号与 API、前端闭环、OIDC 四个可验证切片，详细验收见 [实施顺序](../planning/server-workspace-contract.md#实施顺序与验收)。原型通过仅支持提交顺序选择，不能证明 HTTP 鉴权、路径安全、真实磁盘满、容器、OIDC 或跨设备流程已完成。
