# 协作与文档细则

## 开始与执行

先检查工作区，再读取当前状态和任务对应专题。明确这次是说明、诊断、修改、验证还是发布，沿用用户已给出的具体授权，不把相邻操作自动纳入范围。

需求明确的本地工作直接推进。依赖更新、运行时边界、数据迁移或远程影响出现新选择时，说明影响；只有实质缺失的信息才需要澄清。不要为已授权动作反复制造审批。

工具安装和依赖下载说明版本及落盘位置，优先项目隔离；不改变全局配置来绕过项目问题。后台服务器记录端口、进程与退出方式，任务结束时停止自己启动的实例，除非用户要求保留。

兄弟仓库、用户草稿和其他进程不是本任务可任意修改的资产。并行协作只有确有需求且获得授权时采用，分清文件所有权，不用多个协作者同时改同一共享文件。

## 开发节奏

日常串行开发使用 `dev`，按范围执行本地检查；准备稳定主线 PR 时跑完整 Web 基线；发布前再加真实浏览器、公众号粘贴及外部请求验收。不要把上线级记录前置到每个文案提交，也不要用文案提交的检查强度代表上线已完成。

测试应验证行为和风险。低影响文字调整不额外编写镜像实现的测试；可执行治理门禁则需要负向用例证明错误能阻断合并。失败先定位根因，不通过删除断言、吞掉退出码或跳过 job 来制造成功。

## 文档维护

- `README.md`：产品、运行入口、来源和当前成熟度。
- `AGENTS.md` / `CLAUDE.md`：跨任务都需要的启动约束，两份除标题外一致。
- `docs/governance/` 与 `docs/adr/`：长期规则、决定和原因。
- `docs/status/current.md`：短期范围、当前事实和下一步。
- `docs/records/`：已经发生的检查、限制和证据。

同一事实指定一个详细来源，其他文件用链接和简短摘要引用。治理更改同步工作流、模板、检查器和 ADR；不从历史记录反向生成新的隐含禁令。

## 交付

说明改了什么、为什么、验证结果及剩余事项。分别报告本地通过、远程待启用、真实用户流程未验证等状态。用可点击路径交付，不声称未执行的提交、推送、部署或 Ruleset 已经生效。

## 授权判断与状态保护

开始时核对实际分支、暂存内容、未跟踪文件和跟踪分支。远程跟踪信息可能过期，未执行 fetch 时不要声称已与服务器同步；只读检查不要求为了“最新”自动联网。遇到非预期修改先识别来源，不 reset 工作区来适配原计划。

| 操作                                    | 执行方式                                                                               |
| --------------------------------------- | -------------------------------------------------------------------------------------- |
| 仓库内读写、定向检查、测试与构建        | 在已授权任务内直接完成                                                                 |
| 工具 / 依赖 / 外部资产安装，后台服务    | 说明具体版本、位置、端口、持续时间与清理方式；既有授权已覆盖时直接继续                 |
| 本地提交                                | 按用户明确要求或已确认任务范围执行；检查暂存内容，使用当前身份，不把顺带发现的文件混入 |
| 推送、tag、Release、部署、远程设置      | 必须具备对应目标和动作的授权；前一步通过不自动授权下一步                               |
| 系统 / 全局配置、跨仓库写入、破坏性操作 | 说明实际影响并取得对应授权，不从普通修复请求推导无关权限                               |

用户授权在范围未发生实质变化时持续有效。权限工具或环境要求的确认与项目流程是不同层次，遇到实际拦截应如实说明，不虚构仓库规则要求再次批准。

用户文件和数据的保护优先于环境整洁。仅清理自己创建的临时文件与进程，保留需要交付的证据；不得清空用户草稿、剪贴板历史、浏览器存储或其他工作区来方便测试。自动生成截图与日志应检查是否含敏感信息。

## 结构、错误与兼容

先查现有调用者、类型、校验和公共工具，沿用能够正确表达职责的实现。根因跨越两个模块时可以同时修正，但应解释契约如何恢复一致；不要因“最小 diff”而保留确定的错误，也不要为一次局部修复引入全新框架。

输入失败、存储失败、复制失败和网络失败必须可区分且可定位；只捕获能够恢复或能增加上下文的错误。降级应有明确触发条件和用户可见结果，不能在失败时返回正常状态、空数据或伪造成功反馈。兼容层应说明支持的旧格式、迁移方式与退出条件。

新增手写源码以职责为单位组织，建议不超过 1000 行，1500 行为上限；机器生成文件和既有上游超限文件不做机械追溯拆分。需要调整体量规则时说明实际理由并同步约定，而不是拆成无意义的片段规避限制。

## 根入口准入与交接

规则只有同时满足“跨任务成立、跨阶段成立、必须在开始时生效、仅靠专题路由无法可靠承载”才放入根入口。可路由的详细规则下沉到专题；未落定的讨论无需新建文档，每个小动作也不要求单独记录文件。

两份入口除首行标题外逐字一致，建议在 180 行内，不能超过 250 行。调整协作方式时同时检查两份入口、专题、导航和实际检查脚本；篇幅约束用于人工维护，不能把没有实现的自动检查声称为已生效。

交接至少给出目标与已确认边界、改动位置、实际验证、失败或未验证项、Git 状态、留存产物及后续必要动作。说明哪些设置只是本地模板，哪些已在远程生效；长日志留在适当记录中，正文保留定位所需摘要。
